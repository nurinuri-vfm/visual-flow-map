# visual-flow-map（ビジュアルフローマップ）

**HTML 1枚。操作を——あるいは症状を——押すと、その経路だけが順番に光る。**

**コードベースも、マニュアルも、手順書も**、自己完結したインタラクティブな図に変える [Agent Skill](https://agentskills.io) です。コードが対象なら、エージェントが実際のリポジトリを読み、全ノードの `ファイル:行番号` を実物と突き合わせて検証します。マニュアルが対象なら、同じ形式が「誰も読まない300ページ」を、**「Wi-Fiが繋がらない」を押せば自分の経路だけが見える**ものに変えます。どの手順をクリックしても、そこを通る他の状況が一覧で出ます。

[English → README.md](README.md)

> このプロジェクトを一番早く理解する方法は、デモを開くことです。
> [`demo/conduit-flow-map.html`](demo/conduit-flow-map.html) をダウンロードしてダブルクリックしてください。
> サーバーもインストールもネットワークも不要です。

## 何を図にできるか

**コードベース。** エージェントが実コードを読んでグラフを抽出します。全ノードが `ファイル:行番号` を持ち、リポジトリと突き合わせて検証されます。画面 → API → DB → ジョブ → 外部サービスのように、層をまたぐシステムに最も向きます。

**業務手順・事故対応の経緯。** コードは不要です。レーンは技術層ではなく人と記録になります（誰が・何を・どの順で・どこで分岐し・何を記録したか）。出典は `ファイル:行番号` の代わりに `文書名#条項` や `ヒアリング:役割` で示します。

**マニュアル・手順書。** この形式が最も効くのがここです。300ページのマニュアルを最初から読む人はいません。みんな自分に関係する1箇所を探して、そして見つけられない。この図なら「Wi-Fiが繋がらない」を押すだけで、その経路だけが順番に光ります。さらに任意の手順をクリックすると**そこを通る全ての状況**が出るので、索引では絶対にできない引き方でトラブルシューティングを辿れます。マニュアルの章節番号（`取扱説明書#3.2`）はそのまま ref として使えるため、出典の仕組みが最初から揃っているのも好条件です。

副次的な効果として、**マニュアルをフロー化すると欠落が露出します**。片側しか書かれていない分岐、前提条件が別の章にしかない手順、同じ操作を違う説明で書いている2箇所——これらが構造的に見えるようになります。（コードでも同じことが起きました。RealWorld を図にしたとき、対象側の実バグが2件見つかっています。）

## 何が違うのか

| よくある図 | このスキル |
|---|---|
| 人が手で描く（描いた瞬間から腐る） | エージェントがコードを読んで抽出。作り直しが安い |
| 「たぶん合ってる」 | 全ノードが `ファイル:行番号` を持ち、**実在をリポジトリと突き合わせて検証**。一方で「AがBを呼ぶ」という経路はそうやって検証できないので、各経路は**根拠の強さ**（直接／推定／暗黙／未確認）を申告する。両方を図にスタンプし、未確認の経路は人が確認できるよう一覧に出す |
| 1シナリオ＝1枚のシーケンス図 | 静的な全体図の上に経路を重ねる。共有ノードをクリックすれば**そこを通る操作を逆引き**できる |
| コードを預けるクラウドサービス | **自己完結した HTML 1枚**。CDN もサーバーも不要。コードは手元から出ない |

## デモ

3枚とも、このスキルが生成したものです（[`demo/`](demo/) にあります）。

- **[`order-flow-map.html`](demo/order-flow-map.html)** — *入門*。小さなECサイト（[`demo/sample-app/`](demo/sample-app/)）の web / API / ワーカー / DB を貫く「注文確定・キャンセル・返金再試行・メール送信」。22ノード、参照は全て実在検証済み。
- **[`conduit-flow-map.html`](demo/conduit-flow-map.html)** — *実在OSS・複雑版*。[RealWorld](https://github.com/gothinkster/flask-realworld-example-app) の Flask 実装を、抽出2体＋敵対的検証1体で **19操作・59ノード・130経路** に図化。検証は抽出の事実誤認を4件捕まえ、副産物として対象プロジェクトの実バグも2件見つけました。対象コードは [`demo/conduit-app/`](demo/conduit-app/) に無改変で同梱（MIT）してあるので、59参照の検証を手元で再現できます。
- **[`uptime-kuma-flow-map.html`](demo/uptime-kuma-flow-map.html)** — *最大規模*。[Uptime Kuma](https://github.com/louislam/uptime-kuma)（60k★の監視ツール。server 21.5k行＋UI 33.5k行）を**抽出8体＋敵対的検証2体**で **425ノード・76操作・879経路**・8カテゴリに図化。全425参照が実在検証済みで、経路は根拠を申告しています（直接378 / 推定18 / 暗黙36 / **未確認0**——未確認だった2件は、検証でディスパッチ表が特定できたため格上げしました）。図にする過程で対象側の問題が6件見つかっています（何も削除していないのに成功を返す削除処理など）。入力データと修正の根拠は [`demo/data-uptime-kuma/`](demo/data-uptime-kuma/) にあります。
- **[`incident-flow-map.html`](demo/incident-flow-map.html)** — *手順（コードなし）*。保育園で園児が発熱してから保護者に引き渡すまでを、園の対応マニュアルを出典に図化したもの。レーンは技術レイヤではなく人と記録（保育士 / 看護師 / 連絡 / 保護者 / 記録 / 医療機関）で、ref はソースファイルではなくマニュアルの箇所を指します。

図の中で: ボタンを押すと経路を再生 ・ ノードをクリックで逆引き ・ ドラッグで移動、Ctrl+ホイールで拡大縮小 ・ `#flow=<id>` のディープリンクで特定の経路を共有。

## どう動くのか

このスキルは「描く」だけでなく、**自分の間違いを捕まえるためのパイプライン**を持っています。

```
1. 範囲を決める  リポジトリを担当領域に割る（1領域＝1エージェント）
2. 並列抽出      エージェントが実コードを読んで JSON を書く。全ノードに ファイル:行番号 が必須
3. 監査          audit.js: ID分裂・参照切れ・重複フロー、そして参照の実在をリポジトリと突合せ
4. 敵対的検証    抽出とは別のエージェントが、端から端までの鎖をコードと照合し直す
5. ビルド        build.js が統合・修正適用し、検証結果をHTMLにスタンプする
```

肝は 4 です。抽出エージェントは自信を持って間違えます。RealWorld の実行では監査が全緑だったにもかかわらず、敵対的検証が4件の事実誤認（デコレータ適用順の逆転、中間テーブルの欠落など）を発見しました。修正は根拠コメント付きで `patches.js` に残るので、次に作り直しても消えません。

**何を検証していて、何を検証していないか。** ノードの参照はリポジトリと突き合わせて確認します。ここは機械的です。しかし**経路は検証できません**。実在OSS 4件（Go / Rust / Java マイクロサービス / TypeScript モノレポ）で確かめたところ、Go では辺の約2割がソースのどこにも書かれておらず（ルーティング解決・ミドルウェアの連鎖・チャネル）、Rust では20個の認可ガードがフレームワークから呼ばれるため grep に一切かかりませんでした。だから黙って線を引くのではなく、**各経路をどう確かめたのかを申告させ**、弱いもの（`◇` 暗黙 / `?` 未確認）は図に印を付け、ビルド時に一覧化して人が確認し `patches.js` に記録できるようにしています。**分からないことを分からないと示す図のほうが、どこも確実だと主張する図より価値があります。**

## 使い方

同僚に話しかけるように頼むだけです。

```
このリポジトリの処理フローを可視化して。操作ごとにどこを通るのか追える図にして。
```

```
決済まわりの流れを図にして。来週入る人に見せたい。
```

コードが無いものにも使えます。

```
先週の障害対応の経緯を、対応記録をもとにフロー図にして。
```

```
製品の設定マニュアルをクリックして辿れる図にして。トラブルシューティングの章も含めて。
サポートが「あなたの症状はこの経路です」とリンクを送れるようにしたい。
```

図はあなたが話している言語で書かれます（日本語で頼めば日本語の図になります）。`meta.json` に `"lang": "en"` を書くと、UI のボタンや凡例が英語になります。

## 図を腐らせない

図は腐ります。このスキルの答えは「作り直しを安くする」ことと、「作り直したときに**何が変わったかを見せる**」ことです。

```bash
node skills/visual-flow-map/scripts/build.js \
  --data <データ> --out flow-v2.html --repo <リポジトリ> --diff-base flow-v1.html
```

追加・変更されたノードに **NEW** / **変更** バッジが付き、「前回からの変更点」ボタンが増えて追加された経路だけが光ります。ヘッダには前回比が出ます。変更が無ければ図には何も足されません。

## コストと規模の目安

このスキルは抽出・検証エージェントを並列で走らせるため、実行するとまとまったトークンを消費します。このリポジトリのデモでの実測値です。

| 対象規模 | エージェント | トークン概算 |
|---|---|---|
| 〜2千行 | 抽出2 + 検証1 | 約 40万 |
| 1〜3万行 | 抽出8 + 検証3 | 約 150〜200万 |
| 10万行〜 | 抽出12 + 検証3・2周 | 約 300万〜 |

金額を書いていないのは意図的です。モデル価格は変わりますし、実効単価は契約によって違います。ご自身の単価を掛けてください。

**消費を抑える3つの方法**

- 抽出は機械的な読み取り作業なので中位モデルで足ります。上位モデルは判断が要る敵対的検証だけに使ってください。
- 領域の数がそのまま費用です。まず気になる導線を2〜3本だけ図にして、価値があれば足していく形が確実です。
- 2回目以降は `--diff-base` を使ってください。`patches.js` と `aliases.js` が資産として効くので、初回の3〜5割に収まります。

## 動作要件

- Node.js（`build.js` / `audit.js` / `inspect.js` 用。npm 依存はありません）
- サブエージェントを並列実行できるエージェント環境（Claude Code を想定。Agent Skills 標準に準拠しており、他のハーネス向けに単一エージェントの縮退手順も用意しています）
- スキルの指示は英語（[`SKILL.md`](skills/visual-flow-map/SKILL.md)）で、日本語版（[`SKILL.ja.md`](skills/visual-flow-map/SKILL.ja.md)）を併置しています。**生成される図の言語はこれとは無関係**で、日本語で頼めば日本語の図になります
- 対象リポジトリの読み取り権限。コードは実行もアップロードもしません

## 向いていない場合

無駄な実行を避けるために、正直に書いておきます。

- **単一ファイル・単一レイヤ** — Mermaid かホワイトボードのほうが速いです
- **状態遷移が主題** — 経路ではなく状態と遷移が本題なら、状態遷移図を書いてください
- **実行時のプロファイル** — これは静的にコードを読みます。「実際に何が動いて何秒かかったか」はトレーシングツールの領分です
- **参照型の文書** — APIリファレンス、用語集、仕様一覧表。これらは辞書であって流れではないので、検索と表のほうが優れています

## 手動でビルドする

```bash
node skills/visual-flow-map/scripts/build.js \
  --data demo/data-code --out flow-map.html --repo demo/sample-app
```

`--repo` を渡すと全ノードの `ファイル:行番号` を実在検証し、結果を図にスタンプします。データの隣に置く `meta.json` で題名・レーン・カテゴリ順・用語を設定でき、HTML テンプレートを手で編集することはありません。`audit.js` が抽出データの7項目監査、`inspect.js` が手順の表示と経路の断線検出を行います。

手法の全体は [`skills/visual-flow-map/SKILL.md`](skills/visual-flow-map/SKILL.md) にあります。
