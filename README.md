# visual-flow-map

**One HTML file. Pick an operation — only its path lights up, step by step.**

An [Agent Skill](https://agentskills.io) that turns a system — or a procedure that has no code
at all — into a self-contained interactive diagram you can hand to anyone. For code, agents
read the real repo and every `file:line` reference is machine-verified. For procedures and
manuals, the same shape turns a document nobody reads into something you click through.

[日本語版 → README.ja.md](README.ja.md)

> The fastest way to understand this project is to open a demo: download
> [`demo/conduit-flow-map.html`](demo/conduit-flow-map.html) and double-click it.
> No server, no install, no network.

## What you can map

**A codebase.** Agents read the real code and extract the graph; every node carries a
`file:line` ref verified against the repo. Best for systems that cross layers —
UI → API → DB → jobs → external services.

**A procedure or an incident.** No code required. Lanes become people and records instead of
tech layers: who did what, in what order, where it branched, what got written down. Sources
are cited as `document#section` or `interview:role` instead of `file:line`.

**A manual or a runbook.** This is where the format earns the most. Nobody reads a 300-page
manual front to back — people look for the one part that applies to them, and fail to find it.
Here they press *"Wi-Fi won't connect"* and only that path lights up. And because clicking any
step shows **every situation that passes through it**, a troubleshooting guide becomes
navigable in a way an index never allows. Manual section numbers (`manual#3.2`) work as refs
directly, so the citation layer is already there.

A side effect worth knowing: turning a manual into a flow exposes its gaps. Branches with only
one side written, steps whose precondition lives in another chapter, two sections describing
the same operation differently — these become structurally visible. (The same thing happened
with code: mapping the RealWorld app surfaced two real bugs in it.)

## Why it's different

| Typical diagrams | This skill |
|---|---|
| Hand-drawn — stale the moment they ship | Agents read the code and extract it; regenerating is cheap |
| "Probably correct" | Every node carries a `file:line` ref **verified against the repo**. An edge ("A calls B") *cannot* be verified that way — so each edge declares the strength of its basis instead: direct, inferred, framework-implicit, or unverified. Both are stamped into the diagram, and the unverified ones are listed for a human to confirm |
| One sequence diagram per scenario | Scenario paths are overlaid on a single static map — click any shared node to **reverse-lookup every operation that passes through it** |
| A cloud service that ingests your code | **One self-contained HTML file.** No CDN, no server. Your code never leaves your machine |

## Demos

All three are generated by this skill and live in [`demo/`](demo/).

- **[`order-flow-map.html`](demo/order-flow-map.html)** — *starter*. A small e-commerce app
  ([`demo/sample-app/`](demo/sample-app/)) across web / API / worker / DB: place an order,
  cancel it, retry a refund, send mail. 22 nodes, all refs verified.
- **[`conduit-flow-map.html`](demo/conduit-flow-map.html)** — *real OSS, complex*. The Flask
  implementation of [RealWorld](https://github.com/gothinkster/flask-realworld-example-app),
  mapped by 2 extraction agents + 1 adversarial verifier into **19 operations · 59 nodes ·
  130 edges**. Verification caught 4 extraction errors — and incidentally surfaced 2 real
  bugs in the target project. The target code is vendored unmodified (MIT) under
  [`demo/conduit-app/`](demo/conduit-app/), so you can re-verify all 59 refs yourself.
- **[`uptime-kuma-flow-map.html`](demo/uptime-kuma-flow-map.html)** — *the big one*. [Uptime
  Kuma](https://github.com/louislam/uptime-kuma) (60k★ monitoring tool, 21.5k lines of server
  + 33.5k of UI) mapped by **8 extraction agents + 2 adversarial verifiers** into **425 nodes ·
  76 operations · 879 edges** across eight categories. All 425 node refs verified; edges declare
  their basis (378 direct / 18 inferred / 36 framework-implicit / **0 unverified** — the two that
  started as unverified were promoted after verification found the dispatch table). Mapping it
  surfaced six real problems in the target, including a delete that reports success while
  deleting nothing. Input data and the reasoning behind every fix live in
  [`demo/data-uptime-kuma/`](demo/data-uptime-kuma/).
- **[`incident-flow-map.html`](demo/incident-flow-map.html)** — *a procedure, no code at all*.
  A nursery school handling a child's fever, from onset to handover — built from the school's
  response manual. Lanes are people and records (staff / nurse / contact / parent / logs /
  clinic) instead of tech layers, and refs cite the manual instead of source files.

Inside a diagram: press a button to replay a path · click a node to reverse-lookup ·
drag to pan, Ctrl+wheel to zoom · share one specific path with a `#flow=<id>` deep link.

## How it works

The skill doesn't just draw — it runs a pipeline designed to catch its own mistakes.

```
1. Scope      Split the repo into areas (one agent per area)
2. Extract    Agents read real code in parallel and write JSON — every node needs file:line
3. Audit      audit.js: ID drift, dangling refs, duplicate flows, and ref existence vs the repo
4. Verify     Separate adversarial agents re-check end-to-end chains against the code
5. Build      build.js merges, applies fixes, and stamps the verification result into the HTML
```

Step 4 is the one that matters. Extraction agents are confidently wrong: in the RealWorld
run, audits came back clean while adversarial verification still found 4 factual errors
(a reversed decorator order, a missing join table, and more). Fixes live in a `patches.js`
with the reasoning next to them, so they survive the next regeneration.

**What is and isn't verified.** Node refs are checked against the repo — that part is
mechanical. Edges are not, and cannot be: validating four real codebases (Go, Rust, a Java
microservice monorepo, a TypeScript monorepo) showed that roughly a fifth of Go's edges have
no corresponding line anywhere in the source (mux routing, middleware chaining, channels), and
that Rust's twenty authorization guards are invoked by the framework with no call site to grep.
So instead of quietly drawing those lines, each edge declares how it was established, the
diagram marks the weak ones (`◇` implicit, `?` unverified), and the build lists them so a human
can confirm and record the answer in `patches.js`. A diagram that admits what it doesn't know
is worth more than one that claims certainty everywhere.

## Use

Just ask, in whatever words you'd use with a colleague:

```
Visualize the flows in this repo so I can trace what runs behind each user action.
```

```
Map how the checkout path works — I need to show it to someone new next week.
```

The skill takes it from there. It also works on things that have no code:

```
Turn last week's incident into a flow diagram, based on the response log.
```

```
Make our device setup manual clickable — including the troubleshooting section,
so support can send someone a link to just their path.
```

The diagram is written in the language you're speaking — ask in Japanese and the nodes come
out in Japanese. Set `"lang": "en"` in `meta.json` to switch the built-in UI labels to English.

## Keeping it fresh

Diagrams rot. The answer here is that regenerating is cheap, and that a rebuild can show you
what changed:

```bash
node skills/visual-flow-map/scripts/build.js \
  --data <data-dir> --out flow-v2.html --repo <repo> --diff-base flow-v1.html
```

New and modified nodes get **NEW** / **MOD** badges, a "changes since last build" button
appears that lights up only the added paths, and the header shows the delta. If nothing
changed, nothing is added to the diagram.

## Cost and scale

This skill runs extraction and verification agents in parallel, so a run consumes a
meaningful number of tokens. Measured on the demos in this repo:

| Target size | Agents | Rough tokens |
|---|---|---|
| Under ~2k lines | 2 extract + 1 verify | ~400k |
| 10k–30k lines | 8 extract + 3 verify | ~1.5–2M |
| 100k+ lines | 12 extract + 3 verify, two passes | ~3M+ |

Deliberately no dollar figures: model pricing moves, and your effective rate depends on your
plan. Multiply by your own.

**Three ways to spend less**

- Extraction is mechanical reading — a mid-tier model handles it. Save the top-tier model for
  adversarial verification, where judgment actually matters.
- The number of areas *is* the cost. Map the two or three flows you care about first;
  add areas later if the diagram earns it.
- After the first run, use `--diff-base`. Your `patches.js` and `aliases.js` carry over, so
  later rebuilds land around 30–50% of the initial run.

## Requirements

- Node.js (for `build.js` / `audit.js` / `inspect.js` — no npm dependencies)
- An agent environment that can run subagents in parallel (built for Claude Code; the skill
  follows the open Agent Skills standard, and a smaller single-agent path is documented for
  other harnesses)
- Read access to the target repo. Nothing is executed and nothing is uploaded

## When not to use it

Honest limits, so you don't waste a run:

- **A single file or a single layer** — Mermaid or a whiteboard is faster
- **State machines** — if the subject is states and transitions rather than paths through a
  system, draw a state diagram
- **Runtime profiling** — this reads code statically; use a tracer for what actually ran and
  how long it took
- **Reference-style documents** — an API reference, a glossary, a spec table. Those are
  dictionaries, not flows; search and tables serve them better

## Manual build

```bash
node skills/visual-flow-map/scripts/build.js \
  --data demo/data-code --out flow-map.html --repo demo/sample-app
```

`--repo` verifies every `file:line` ref and stamps the result into the diagram. A `meta.json`
next to the data configures the title, lanes, category order and wording — the HTML template
is never edited by hand. `audit.js` runs the seven checks on extracted data; `inspect.js`
prints a flow's steps and reports breaks in the chain.

See [`skills/visual-flow-map/SKILL.md`](skills/visual-flow-map/SKILL.md) for the full method.
